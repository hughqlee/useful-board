# useful-board 설계: 제품 원칙과 아키텍처

2026-11-19 초안. 원본 문서: https://claude.ai/artifact/GpGaRFyp5yhYjtcQvrnniH

## 결론

이 제품은 **목표를 세우고, 그 목표를 어떤 지표로 볼지 구체화하고, 정말 필요한 일이 진행되도록 돕는다.** 대시보드는 그 수단이고, 별도 앱이나 창이 아니라 Claude 데스크톱 같은 에이전트 툴 안에서만 돈다.

1. 출발점은 **목표(Goal)**다. 목표마다 지표 항목(Item: 질문·지표·비교 기준·행동 규칙)과 지금 할 **일(Action)**이 붙는다.
2. 한 화면, 항목 **최대 7개**. 정상은 접고 예외만 펼친다. 오래된 데이터는 숫자 대신 "오래됨"으로 보인다.
3. **별도 앱·창 없음.** 보드는 에이전트 대화 안의 카드로만 보이고, 봐야 할 때가 되면 에이전트가 먼저 말한다.
4. 코어는 **로컬 MCP 서버 + SQLite**. Claude 플러그인은 그 위의 목표 인터뷰·주간 점검 스킬이다.
5. 첫 사용자는 **개인**, 직업은 가리지 않는다(개발자 한정 아님).

## 제1원칙: 대시보드는 왜 쓸모없어지는가

대시보드는 주의력을 소비해 판단을 산다. 가치 = (행동이 바뀔 확률 × 그 행동의 가치) − 주의력 비용. 쓸모없는 대시보드는 이 식의 항 중 하나가 0이거나 비용이 가치보다 크다.

| 근본 원인 | 일어나는 일 | 식에서 무엇이 깨지나 |
| --- | --- | --- |
| 별도 앱·창 | 대시보드마다 앱·탭·로그인이 따로다. 일하는 곳을 떠나야 보이니 아무도 안 간다 | 보는 횟수 0 |
| 목표 없음 | 무엇을 이루려는지 없이 "데이터가 있으니까" 넣는다 | 행동 확률 0 |
| 비교 기준 없음 | 숫자 하나로는 좋은지 나쁜지 판단 불가 | 행동 확률 0 |
| 일로 이어지지 않음 | 나쁜 숫자를 봐도 다음 할 일이 정해져 있지 않다 | 행동 확률 0 |
| 신뢰 붕괴 | 갱신 중단, 정의 변경. 틀린 숫자 한 번이면 전체를 안 믿는다 | 행동 확률 0 |
| 누적과 장식 | 추가만 하고 삭제는 없다. 차트 종류·색이 읽기를 방해한다 | 주의력 비용 증가 |

바이브 코딩은 만드는 비용을 0에 가깝게 낮췄지만 위 원인은 하나도 건드리지 않는다. 오히려 대시보드가 늘수록 열어야 할 창도 늘었다. 병목은 이제 **무엇을 볼지 정하는 일, 계속 믿게 유지하는 일, 그리고 이미 일하는 자리에서 보이게 하는 일**이다.

## 제품 원칙

원인 하나마다 그것을 구조적으로 막는 규칙을 둔다. 권고가 아니라 시스템이 강제하는 규칙이다.

| 원칙 | 막는 원인 | 강제 방법 |
| --- | --- | --- |
| 1. 일하는 곳에서 보인다 | 별도 앱·창 | 에이전트 대화 안에서만 표시. 경고선을 넘으면 에이전트가 먼저 알린다 |
| 2. 목표 없이는 항목도 없다 | 목표 없음 | 모든 Item은 Goal에 속하고, question·action_rule이 비면 검증 실패 |
| 3. 모든 숫자는 비교와 함께 | 비교 기준 없음 | 목표치, 경고선, 직전 기간 중 하나 필수 |
| 4. 지표는 일로 이어진다 | 일로 이어지지 않음 | 주의 상태가 되면 action_rule에서 Action을 만들고 끝날 때까지 추적 |
| 5. 신선도와 출처를 항상 표시 | 신뢰 붕괴 | 갱신 주기를 넘기면 숫자를 숨기고 "오래됨" 표시 |
| 6. 한 화면, 최대 7개 | 누적과 장식 | 초과 시 추가 거부. 빼야 넣을 수 있다 |
| 7. 모든 항목에 만료일 | 누적 | 만료일에 "유지/삭제" 검토 요청 |
| 8. 예외만 펼친다 | 주의력 비용 | 정상 항목은 한 줄로 접힘 |
| 9. 스펙이 원본, 화면은 파생 | 장식, 이식성 | 렌더러는 스펙만 보고 그린다. 스타일 옵션 없음 |

마지막 원칙이 나머지를 가능하게 한다. 화면 코드가 아니라 구조화된 스펙을 고치기 때문에 제약을 검사할 수 있고, 어떤 에이전트든 같은 규칙 아래서 편집한다.

## 데이터 모델

최상위는 **Goal**이고, 그 아래 **Item**(질문 + 지표 + 비교 + 행동 규칙)과 **Action**(지금 할 일)이 붙는다. 목표 → 관찰 → 일의 흐름이 그대로 스키마다.

| 객체 | 필드 | 역할 |
| --- | --- | --- |
| Board | owner, goals[], 표시되는 Item ≤ 7 | 한 사람의 한 화면 |
| Goal | title, why, due, state | 이루려는 것. 예: 6월까지 10kg 감량, 연말까지 초고 완성 |
| Item | goal_id, question, metric, compare, action_rule, refresh, review_by | 목표가 잘 가고 있는지 보는 판단 하나 |
| Metric | source, query/compute, unit | 값을 어디서 어떻게 얻는가. 수동 입력도 출처다 |
| Snapshot | item_id, value, observed_at, source_ref | 값의 시계열. 추세·직전 비교의 근거 |
| Status (계산값) | ok · attention · stale · unknown | 펼칠지, 에이전트가 먼저 말할지 결정 |
| Action | goal_id, item_id, text, due, state(open · done · dropped) | 지금 해야 할 일. Item이 attention이 되면 제안된다 |
| Note | item_id, snapshot_id, text | "이 값은 왜?" 특정 시점 값에 단 기록 |

스펙 형식은 [`schema/board.schema.json`](../schema/board.schema.json), 예시는 [`examples/savings.board.yaml`](../examples/savings.board.yaml)에 있다.

Status 규칙은 단순하다. 마지막 Snapshot이 refresh 주기보다 오래되면 stale, warn을 넘으면 attention, 값이 없으면 unknown, 나머지는 ok다. Action을 한 번도 만들지 않고 review_by에 이른 Item은 삭제 후보로 제안된다.

## 위젯·레이아웃 제약

위젯은 4종류만 둔다. 사용자는 종류를 고르지 않고, 지표의 형태가 종류를 정한다.

| 위젯 | 쓰는 경우 | 보여주는 것 |
| --- | --- | --- |
| Number | 현재 값 하나가 답일 때 | 값, 비교(목표 대비·직전 대비), 작은 추세선 |
| Trend | 방향이 답일 때 | 한 지표의 시계열 + 경고선 |
| List | "무엇을 처리해야 하나"가 답일 때 | 조건에 걸린 항목 최대 5개 |
| Check | 예/아니오가 답일 때 | 통과·실패와 마지막 확인 시각 |

화면은 별도 창이 아니라 에이전트 안에 그려진다. 레이아웃은 자유 배치가 아니라 순서다.

- 표시 위치는 대화 응답 안의 보드 카드다. 대화 옆 패널도 쓰지 않는다. 독립 웹 앱, 브라우저 탭, 별도 로그인은 없다.
- 목표별로 묶는다. 목표 안에서는 attention → stale → unknown → ok 순으로 자동 정렬한다.
- 열린 Action은 해당 목표 바로 아래에 보인다. 보드를 보는 것과 다음 일을 아는 것이 한 번에 끝난다.
- ok 항목은 한 줄로 접힌다. 모두 ok면 보드는 "모두 정상, 마지막 확인 09:00" 한 줄이다.
- 파이·게이지·이중 축·색 테마 옵션은 없다. 색은 상태(주의·오래됨)에만 쓴다.
- 모든 값 옆에 출처와 관측 시각이 붙는다. "이건 왜?"라고 물으면 에이전트가 질문·행동 규칙·최근 Note로 답한다.

## 개인용과 공유·협업

MVP는 개인용이다. 공유는 그다음 단계이고 원칙은 같다. 공유의 단위는 화면이 아니라 **Item**이고, 공유도 별도 앱이 아니라 각자의 에이전트 안에서 일어난다.

- **개인 보드**: 한 사람에 보드 하나. 목표 몇 개와 Item 7개 이하.
- **공유(MVP 이후)**: 다른 사람의 에이전트가 같은 MCP 서버에 접속해 Item을 참조한다. 복사하지 않으므로 숫자가 어긋나지 않는다.
- **변경은 제안으로**: 남의 Item을 바꾸려면 스펙 diff를 제안하고 주인이 수락한다.
- **대화는 값에 붙는다**: Note는 특정 시점의 Snapshot에 달린다. 다음 사람이 같은 걸 다시 묻지 않는다.
- **함께 하는 목표**: 공동 목표의 Action은 담당자가 정해지고, 각자 에이전트에서 자기 일로 보인다.

## 배포 형태: MCP 서버가 코어

코어는 MCP 서버로 둔다. 스펙·Snapshot·Note는 여러 사람과 여러 에이전트가 같이 읽고 쓰는 공유 상태이고, 공유 상태는 한 곳에 있어야 한다. MCP는 Claude, Cursor, ChatGPT 등 어떤 에이전트에서든 그 한 곳에 접근하는 공통 인터페이스다. 플러그인을 코어로 두면 규칙이 프롬프트에 살고, 에이전트가 바뀌면 제약도 사라진다.

```
데이터 출처 ──(에이전트 커넥터로 읽기)──> 에이전트(Claude + 플러그인, Cursor 등)
                                              │  MCP 도구 호출
                                              ▼
                                       MCP 서버(코어) ──> 보드 카드(에이전트 대화 안)
                                              │
                                              ▼
                                       SQLite 파일(서버 프로세스만 엶)
```

| 층 | 담는 것 | 왜 여기에 |
| --- | --- | --- |
| MCP 서버 (코어) | 스펙 검증, Snapshot 저장, Status 계산, Action·Note, SQLite 단독 소유 | 제약은 코드가 강제해야 우회할 수 없다 |
| 에이전트 (표시·대화) | 보드 카드 표시, 경고 알림, Action 진행 돕기 | 사람이 이미 일하는 곳이다. 별도 창을 만들지 않는다 |
| Claude 플러그인 | 목표 인터뷰 스킬, 주간 점검 스킬, 갱신 스케줄, 첫 셋업 | Claude에서의 경험. 없어도 코어는 다른 에이전트에서 돈다 |

MCP 도구는 작게 유지한다: `board_get`, `goal_set`, `item_propose`, `item_remove`, `snapshot_record`, `board_evaluate`, `action_add`, `action_update`, `note_add`. 추가는 항상 `item_propose`를 거치고, 서버가 원칙 2·3·6·7을 검사해 거부 사유를 돌려준다.

**저장은 SQLite, 첫 셋업에서 함께 구성한다.** 플러그인을 설치하면 첫 셋업이 MCP 서버를 올리고 SQLite 파일 하나를 만든다. 스펙·Snapshot·Action·Note는 모두 이 파일에 있고, board.yaml은 검토와 이식을 위한 내보내기·가져오기 형식이 된다.

SQLite로 충분한 이유는 데이터의 크기와 쓰기 패턴이다. 보드당 항목은 7개 이하이고, 하루 몇 번 갱신해도 수백 명이 몇 년을 써도 수백 MB를 넘기 어렵다. 쓰기는 가끔 일어나고 대부분은 읽기다.

공유의 규칙은 하나다. **SQLite 파일은 MCP 서버 프로세스 하나만 열고, 다른 사람과 에이전트는 MCP 서버를 통해서만 접근한다.** 네트워크 드라이브나 클라우드 동기화 폴더로 파일을 직접 공유하지 않는다. 그러면 잠금이 깨져 파일이 손상될 수 있다. WAL 모드를 켜고, 백업은 서버가 주기적으로 파일 스냅샷을 떠서 한다. 개인용에서는 서버가 내 컴퓨터에서 로컬로 돌아 인증이 필요 없다. 공유 단계에서만 서버를 모두의 에이전트가 닿는 곳에 두고 토큰 인증을 붙인다.

**데이터 수집은 에이전트와 서버가 나눠 한다.** 에이전트는 이미 Sheets, GitHub, Stripe 같은 커넥터를 갖고 있다. 서버가 모든 출처의 커넥터를 다시 만들 필요가 없다. 예약 실행된 에이전트가 값을 읽어 `snapshot_record`로 넣고, 서버는 출처와 시각을 함께 저장한다. 서버가 처음부터 떠 있으므로, 단순 출처(HTTP JSON, CSV, 외부 DB 쿼리)는 MVP부터 서버가 예약대로 직접 당긴다.

## MVP 범위와 다음 결정

MVP는 개인 한 사람이 목표 1~3개를 세우고, 4주 동안 에이전트 안에서만 보드를 쓰는 것까지다. 직업은 가리지 않는다.

1. 스키마와 검증기: Goal·Item·Action, 원칙 2·3·6·7을 코드로 강제
2. 로컬 MCP 서버: 도구 9개 + 첫 셋업에서 SQLite 파일 생성(스키마, WAL, 백업 주기). 인증 없음
3. 보드 카드: 에이전트 대화 안에 그리는 한 화면
4. Claude 플러그인: 목표 인터뷰 스킬(목표 → 지표 → 행동 규칙), 매일 갱신과 경고 알림, 주 1회 점검 스킬
5. 검증할 목표 예: 저축, 체중·운동, 책 집필, 구직, 작은 가게 매출

성공 기준은 "예쁜가"가 아니라 쓸모다. 4주 동안 별도 창을 열지 않고 주 1회 이상 보드를 봤고, Item의 절반 이상이 완료된 Action을 한 번 이상 만들었다.
